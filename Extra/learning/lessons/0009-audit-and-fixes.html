L9 — Auditoria de Arquitetura: O Que Estava Quebrado

Depois que o agente passou a funcionar, fizemos uma auditoria completa. O resultado foi humilde: tinha bugs críticos escondidos por trás de uma aparência de "funcionando". Essa lição conta o que encontramos e como corrigimos.

O que parecia funcionar

  • O grafo compilava e rodava
  • Tickets geravam respostas
  • 39 testes da API passavam
  • Decisões apareciam no output

O que realmente estava quebrado

🔴 CRÍTICO 1: "Ação" era mentira

O nó act fazia só interrupt() e retornava um trace entry. Nunca chamava a API (POST/PATCH). O agente dizia "AGIR" mas não fazia nada.

Depois: O nó agora executa POST/PATCH real na API (reprocess, specialist, retrain, update_config).

🔴 CRÍTICO 2: decision=None para unavailable

O route_after_quality mandava unavailable direto para escalate, pulando o nó decide. Resultado: decision=None em todos os unavailable.

Depois: unavailable agora vai para decide, que define decision="escalate" com justificativa.

🟡 ALTO: Cache nunca invalidava

O hash do cache era só do contexto. Trocou o prompt? O cache antigo continuava valendo.

Depois: A chave inclui AGENT_VERSION. Mudar a versão invalida o cache automaticamente.

🟡 ALTO: tools_called duplicava entries

O nó investigate retornava a lista inteira. O state usa operator.add que appenda. Resultado: duplicatas e budget de retry estourava cedo.

Depois: investigate retorna só os NOVOS tools daquela passada. O operator.add concatena corretamente.

🟡 ALTO: Trajectory assertions incompletas

Só contavam 5 GET categories (baseline/analyses/rms/spectrum/data_quality). Não detectavam knowledge, models, asset_info, nem ações POST.

Depois: Cobertura expandida para knowledge, models, asset_info.

🟢 MÉDIO: Código morto e dependências faltando

agent/tools.py antigo conflitava com agent/tools/ package. pyproject.toml não existia (clone limpo = import error). is_within_trace() nunca chamado. 5 campos no state nunca escritos.

Depois: Código morto removido. pyproject.toml criado. State limpo.

O processo de auditoria

1. Li TODOS os arquivos-chave (agent/, eval/, api/)
2. Rodei o agente em cada cenário e comparei com gabarito
3. Tracei cada chamada HTTP/LLM pra ver onde quebrava
4. Fiz a lista de bugs por severidade
5. Criei branch feature/fix-critical-issues
6. Corrigi em ordem de severidade
7. Testei cada fix com testes unitários + runtime
8. Merge na main quando tudo passou

Teste seu entendimento

Pergunta 1
Por que o bug decision=None era perigoso?
Resposta

Porque o avaliador (trajectory assertion) verificava se decision era igual ao gabarito. Quando era None, sempre falhava — mesmo que o agente tivesse tomado a decisão correta no decide (que pulava).

Pergunta 2
Por que cache sem invalidação é um problema para avaliação?
Resposta

Se você muda o prompt e roda a avaliação, o cache retorna decisões do prompt antigo. A avaliação mede o comportamento antigo, não o novo. Você pensa que melhorou mas não melhorou.
