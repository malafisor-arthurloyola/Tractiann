L11 — Docker, Postgres e Observabilidade

O agente não precisa só de um bom brain (o LLM). Ele precisa de um bom sistema nervoso: como registrar o que feu, comparar desempenho entre versões, e ter um historial para debug. É aí que entram o Docker, o Postgres e o Phoenix.

Docker: O Container do Agente

Docker encapsula serviços como Postgres e Phoenix em ambientes isolados. No nosso projeto, o docker-compose.yml define dois serviços:

services:
  postgres-agent:
    image: postgres:16-alpine
    container_name: tractian-agent-postgres
    environment:
      POSTGRES_USER: tractian
      POSTGRES_PASSWORD: tractian_dev
      POSTGRES_DB: tractian_agent
    ports:
      - "5432:5432"
    volumes:
      - postgres_data:/var/lib/postgresql/data

  phoenix:
    image: arizephoenix/phoenix:latest
    container_name: tractian-agent-phoenix
    ports:
      - "6006:6006"

Como Rodar

# Sobe Postgres e Phoenix em background
make up

# Inicializa a tabela execucoes no Postgres
make postgres-init

# Acessa o Phoenix (dashboard de tracing) em http://localhost:6006
make phoenix-up

Postgres: O Diário do Agente

O Postgres salva cada execução relevante do agente. Isso permite comparar versões (v1 vs v2) e entender padrões (qual motivo de escalonamento é mais comum?).

Schema da Tabela execucoes

CREATE TABLE IF NOT EXISTS execucoes (
    id              SERIAL PRIMARY KEY,
    ticket_id       TEXT NOT NULL,
    agent_version   TEXT NOT NULL DEFAULT 'v1',
    user_id         TEXT,
    asset_id        TEXT,
    decision        TEXT,           -- 'orient' | 'act' | 'escalate'
    quality_verdict TEXT,           -- 'ok' | 'partial' | 'incomplete' | 'unavailable'
    data_gaps       JSONB,          -- o que faltou
    trace           JSONB,          -- chamadas a API + justificativas
    response        TEXT,
    created_at      TIMESTAMPTZ DEFAULT NOW()
);

Comparando Versoes

A funcao chave e compare_versions(v1, v2) em agent/logging/postgres.py. Ela executa uma query que cruza as decisoes de cada versao:

SELECT * FROM (
    SELECT
        COALESCE(a.decision, b.decision) AS decision,
        COALESCE(a.quality_verdict, b.quality_verdict) AS quality_verdict,
        COALESCE(a.n, 0) AS v_a,
        COALESCE(b.n, 0) AS v_b
    FROM (SELECT decision, quality_verdict, COUNT(*) n FROM execucoes
          WHERE agent_version = 'v1' GROUP BY decision, quality_verdict) a
    FULL OUTER JOIN (SELECT decision, quality_verdict, COUNT(*) n FROM execucoes
          WHERE agent_version = 'v2' GROUP BY decision, quality_verdict) b
      ON a.decision = b.decision AND a.quality_verdict = b.quality_verdict
) t
ORDER BY v_a + v_b DESC;

Isso gera uma tabela comparativa que voce pode ver no terminal via make compare v1 v2.

Phoenix: O Raio-X do LLM

Enquanto o Postgres guarda o resumo, o Phoenix (Arize) guarda cada chamada ao LLM: o prompt enviado, a resposta recebida, tokens e latencia. E gratuito e open-source (usamos em vez do LangSmith pago).

Como Funciona?

  • O agente usa opentelemetry para enviar spans para o Phoenix.
  • O Phoenix roda em Docker e visualiza esses traces em um dashboard web.
  • Quando PHOENIX_ENABLED=1 no .env, cada chamada ao LLM e registrada automaticamente via LangChainInstrumentor.
Dica: Para ver o que o LLM realmente pensou (e por que ele errou), abra o Phoenix, encontre o trace do ticket problemático, e inspecione o prompt completo.

Teste seu entendimento

Pergunta 1
Por que usamos MEMORYSAVER em vez de PGCHECKPOINTER para o grafo?
Resposta

MemorySaver e mais simples e ideal para desenvolvimento/testes. Ele guarda o estado na memoria do processo. Para producao, onde multiplos processos ou reinicios aconteceriam, usariamos o Postgres como checkpointer para garantir que o estado de uma interrupcao (HITL) persista.

Pergunta 2
O que acontece se o Postgres nao estiver rodando?
Resposta

O logger (log_execution) retorna False silenciosamente. O agente continua funcionando normalmente, mas nenhuma execucao sera registrada no historico. E um degrade-safe.
