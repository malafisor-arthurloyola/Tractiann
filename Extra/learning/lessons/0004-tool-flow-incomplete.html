L4 — Fluxo das Tools: incomplete, check e outra tool

Sua pergunta foi: "como assim acessar outras tools? o incomplete é pra cada requisição específica? onde fica o check?" Vou responder com um exemplo real, mostrando o código.

A resposta curta

O quality check verifica o mode do envelope de cada requisição que o agente fez. Se um dado veio partial ou unavailable, ele pode mandar o agente buscar os dados que faltaram em outra tool sobre o mesmo ativo — porque o ativo tem vários tipos de dados (baseline, RMS, espectro, qualidade).

Exemplo concreto: ticket TKT-INV-05

"Tô vendo o RMS do compressor subindo há duas semanas, mas não recebi insight nenhum. Cadê o diagnóstico?"

Ativo: asset_C710 · Usuário: usr_sofia

Passo 1 — investigate chama 5 tools em sequência

O nó investigate não chama uma tool só. Ele faz 5 requisições diferentes sobre o mesmo ativo:

#ToolO que busca
1GET /assets/asset_C710/baselineO "normal" aprendido
2GET /assets/asset_C710/analysesDiagnósticos automáticos
3GET /assets/asset_C710/rmsSérie de vibração
4GET /assets/asset_C710/spectrumFFT (frequências)
5GET /assets/asset_C710/data-qualityCompletude dos dados

Cada requisição retorna um envelope próprio com seu mode.

Passo 2 — cada tool retorna seu envelope

Tool 1 (baseline):  {"mode": "partial",  "data": {"state": "established"}, "notes": "Informação parcial..."}
Tool 2 (analyses):  {"mode": "complete", "data": {"analyses": [...]}}
Tool 3 (rms):       {"mode": "complete", "data": {"series": [...], "alarm_threshold": 4.2}}
Tool 4 (spectrum):  {"mode": "unavailable", "data": {}, "notes": "Indisponibilidade temporária..."}
Tool 5 (data_quality): {"mode": "partial", "data": {"completeness": 0.85}}

Note que o spectrum veio unavailable e o baseline veio partial. As outras estão ok.

Passo 3 — quality_check avalia TUDO junto

O quality_check olha os envelopes que chegaram e decide:

  • Baseline = partial → dados parciais, mas tem algo.
  • Análises = complete → ok.
  • RMS = complete → ok.
  • Spectrum = unavailable → sem espectro.
  • Data quality = partial → completude 85%, aceitável.

O quality_check retorna: "ok com ressalvas" — tem dados suficientes pra decidir, mas o espectro faltou. O agente pode:

  1. Seguir com o que tem (baseline parcial + análises completas + RMS completo) — Decide com base nisso.
  2. Tentar spectrum de novo — Mas se veio unavailable, provavelmente vai vir de novo.
  3. Escalar — Se o espectro for essencial pro diagnóstico.

Os 3 cenários do quality_check

Cenário O que o quality_check vê Veredicto O que acontece no grafo
ok Todas as tools retornaram complete ok Segues pro decide
partial Algumas tools vieram partial (campos faltando) partial Segues pro decide — o LLM sabe que faltam detalhes
incomplete Dados muito incompletos (ex: analyses vazio) incomplete Volta pro investigate pra tentar de novo
unavailable Baseline unavailable ou conflict unavailable Vai direto pra escalate

Onde fica o check no código

# agent/graph/nodes.py — função quality_check()

def quality_check(state):
    baseline = state.get("baseline")          # Envelope da tool 1
    analyses = state.get("analyses", [])      # Resposta da tool 2

    # Verifica o MODE do envelope do baseline
    if baseline and baseline.get("mode") in ("unavailable", "conflict"):
        return {"quality_verdict": "unavailable"}  # → escalate

    if baseline.get("mode") == "partial":
        return {"quality_verdict": "partial"}      # → decide (com ressalva)

    # Verifica se tem análises
    if not analyses:
        return {"quality_verdict": "incomplete"}   # → volta pra investigate

    return {"quality_verdict": "ok"}               # → decide

"Outra tool" significa o quê exatamente?

Quando o grafo volta pra investigate, o agente não repete as mesmas 5 tools automaticamente. Ele pode:

  • Tentar uma tool diferente que não foi chamada antes (ex: searchKnowledge(q="procedimento manutenção compressor") pra buscar procedimento de manutenção que ele não tinha consultado).
  • Tentar a mesma tool com parâmetros diferentes (ex: mudar o seed pra forçar resposta completa).
  • Buscar conhecimento via searchKnowledge se o diagnóstico automático falhou.

Na prática, o nosso investigate atual é simplificado — ele sempre chama as mesmas 5 tools. A arquitetura real (que vamos implementar quando o LLM estiver integrado ao grafo) deixa o agente escolher quais tools chamar com base no que já tem.

Teste seu entendimento

Pergunta 1
Se o baseline veio partial e o spectrum veio unavailable, qual é o veredicto do quality_check?
Resposta

partial. O baseline parcial é aceito (o agente segue pro decide com ressalva). O spectrum unavailable é anotado mas não impede a decisão — o agente pode decidir sem o espectro.

Pergunta 2
O quality_check verifica o envelope de cada tool individualmente, ou verifica tudo de uma vez?
Resposta

Ele recebe o estado com todos os envelopes e verifica os que são críticos (baseline e analyses). No código atual, ele checa o baseline primeiro e depois se tem análises. Não verifica todas as 5 tools — é uma verificação seletiva.

Pergunta 3
Quando o grafo volta pra investigate, ele sempre repete as mesmas tools?
Resposta

No código atual, sim (é simplificado). Na arquitetura ideal, o LLM decide quais tools chamar com base no que já tem — pode buscar uma tool diferente (ex: searchKnowledge) ou tentar a mesma com parâmetros diferentes.
