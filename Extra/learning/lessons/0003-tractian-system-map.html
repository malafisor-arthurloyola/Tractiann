L3 — Mapa do Sistema Tractian

A API industrial tem 7 blocos. O agente navega por eles como um engenheiro de suporte visitando setores diferentes da fábrica. Cada bloco responde uma pergunta diferente sobre o ativo do cliente.

Os 7 blocos

# Bloco Pergunta que responde Endpoints
1 Contexto Quem é o cliente? Quais ativos tem? GET /companies/{id}, GET /companies/{id}/assets, GET /users/me
2 Ativos O que é essa máquina? Qual sua config? GET /assets/{id}, GET /assets/{id}/analyses, PATCH /assets/{id} ⚠️
3 Análises O modelo detectou algo? Qual a evidência? GET /analyses/{id}, POST /analyses/{id}/reprocess ⚠️, POST /analyses/{id}/request-specialist ⚠️
4 Dados Técnicos Como estão os sensores? Qual o espectro? GET /assets/{id}/baseline, GET /assets/{id}/rms, GET /assets/{id}/spectrum, GET /assets/{id}/data-quality
5 Modelos Qual modelo analisa esse ativo? Precisa de retreino? GET /models/{id}, POST /models/{id}/request-retraining ⚠️
6 Conhecimento Existe procedimento ou glossário sobre isso? GET /knowledge/search?q=..., GET /knowledge/{docId}
7 Ações Preciso escalar esse caso pra humano? POST /cases/{id}/escalate ⚠️

⚠️ = ação de impacto (exige justificação + x-user-id)

Fluxo típico do agente (uma visita à fábrica)

Imagine que um cliente abre um ticket dizendo: "O motor M-605 tá vibrando estranho, queria entender o que tá acontecendo". O agente faz isso:

  1. Contexto: Pega os dados do cliente via getCurrentUser. Descobre empresa, permissões e o ID do ativo.
  2. Baseline: Verifica se o "estado normal" do motor tá ok via getBaseline. Se learning → não confia no diagnóstico.
  3. Análises: Lista diagnósticos automáticos via listAnalyses. Verifica se tem insight com detection_mode: baseline ou symptom.
  4. Dados Técnicos: Puxa RMS e espectro (getRmsSeries, getSpectrum) pra entender o padrão de vibração. Verifica qualidade dos dados via getDataQuality.
  5. Conhecimento: Busca procedimentos de manutenção (searchKnowledge) pra orientar o cliente.
  6. Decisão: Com tudo isso, decide se orienta (explica), age (reprocessa análise, solicita especialista) ou escala pro time.

Os nós do Grafo LangGraph

O grafo é a mente do agente — decide o que fazer com tudo isso.

investigate → quality_check → decide → respond / act / escalate
      ↑              ↓
      └──────── incompleto (loop)
  • investigate: chama as tools pra coletar dados (bloco 1–6).
  • quality_check: verifica o [[Envelope de Resposta]] (Lição 2). É o dono da política: aceitar / repetir / escalar.
  • decide: alimenta o LLM com tudo e escolhe: orientar, agir ou escalar.
  • respond / act / escalate: executa a decisão.

Teste seu entendimento

Pergunta 1
O agente recebe um ticket e descobre que o baseline está learning. Ele deve confiar no próximo insight que encontrar?
Resposta

Não. Baseline learning significa que o modelo ainda não aprendeu o "normal" daquele ativo. Insights com detection_mode: baseline são pouco confiáveis. O agente deve considerar isso antes de confiar — pode ser necessário escalar ou buscar evidência de outro tipo (ex: espectro).

Pergunta 2
Quais blocos a tool getBaseline e getSpectrum pertencem? Quantos endpoints tem no bloco "Dados Técnicos"?
Resposta

Ambas pertencem ao bloco Dados Técnicos. São 4 endpoints: baseline, RMS, espectro e qualidade dos dados.

Pergunta 3
O que acontece no grafo quando o quality_check retorna incomplete?
Resposta

O grafo volta para investigate (loop) pra tentar buscar o dado faltante em outra tool. Se depois de algumas tentativas ainda estiver incompleto, o quality_check pode mandar direto pra escalate.
