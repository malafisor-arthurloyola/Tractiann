L1 — Por que a nossa arquitetura tem 3 riscos (e o que vamos fazer)

Antes de apertar o botão "construir", precisamos entender por que a arquitetura que desenhamos no AGENTS.md tem 3 pontos de atenção. Estas são as lições que o código vai recompensar a gente por ter entendido cedo.

Revisão rápida (30s)

Nosso sistema é em camadas: 
Streamlit (UI) → Agente (LangGraph) → Tools (MCP) → API Tractian
O agente recebe um ticket, investiga dados, e decide entre orientar / agir / escalar. Cada camada é um seam (costura): um ponto onde uma peça pode ser trocada sem quebrar as outras.

Risco 1 — A camada MCP é "rasa" (duplicação)

RISCO 1 · shallow module

As 17 tools vão todas fazer a mesma dança:

  1. montar a URL do endpoint,
  2. mandar o header x-user-id,
  3. chamar o HTTP via httpx,
  4. interpretar o envelope de resposta (complete/partial/inconclusive/conflict/unavailable).

Se cada tool reescrever essas 4 ações, temos um módulo raso: a interface (jeito de usar) fica quase tão complexa quanto o que ela faz. E o pior: se a API mudar o formato do envelope amanhã, temos que consertar 17 lugares e quase com certeza esqueceremos um.

Solução: criar um único helper central (fetch_envelope) que faz as 4 ações uma vez. As 17 tools ficam curtas: dizem qual operação querem, recebem o envelope já tratado.
🎮 Minecraft: 17 fornalhas, cada uma precisando de carvão manualmente, vira um único sistema de transporte de carvão que abastece todas. Trocar a fonte de energia = mexer num lugar só.

Risco 2 — Quem decide quando a resposta vem "incompleta"?

RISCO 2 · policy sem dono

A regra "resposta incompleta → repetir, buscar dado faltante, ou escalonar" está escrita no briefing, mas não está definido em qual nó do grafo ela vive. Sem um dono, ela se espalha por vários nós e fica inconsistente.

Solução: um nó dedicado de "quality check" no grafo do LangGraph. Toda resposta passa por ele: aceitar 🟢, repetir 🔄, ou buscar dado faltante em outra tool. Uma sala só, regra centralizada.
🎮 Minecraft: a regra do vilarejo ("se o item vier quebrado, conserta ou chama o ferreiro") precisa morar na casa de um morador. Se estiver escrita em todas as portas, mudar a regra = reescrever tudo, e os moradores se contradizem.

Risco 3 — Nada registra "por que decidimos isso"

RISCO 3 · sem registros

Dois documentos salvam o cérebro do projeto:

  • CONTEXT.md — glossário de domínio: define termos-chave ("baseline" = o normal daquele ativo específico, não uma norma genérica).
  • docs/adr/ — registros de decisão (ADRs): por que escolhemos Groq, por que MCP, etc.
🎮 Minecraft: o livro de encantamentos guarda o conhecimento do mundo; o baú de anotações guarda o porquê. Sem eles, cada encantador (e cada IA futura) interpreta os termos do jeito que quiser.
