L7 — Observabilidade: Postgres e Phoenix

O agente está rodando. Mas como você sabe o que ele fez, por que decidiu aquilo, e se uma nova versão melhorou? É aí que entra a observabilidade.

Sobre a escolha: a LangSmith (da LangChain) faz esse papel, mas é paga. Usamos o Phoenix (Arize), que é o equivalente gratuito e open source — mesmo padrão OpenTelemetry. (Ver L11 para detalhes de infraestrutura).

Duas ferramentas, dois níveis

Ferramenta Nível O que guarda Quando usar
Postgres Log de execuções Ticket, agente_version, decisão, gaps, trace, timestamp Comparar versões, métricas agregadas, auditoria
Phoenix Trace detalhado + dashboard Cada chamada ao LLM (prompt/output/tokens/latência) em dashboard :6006 Debugar por que o LLM respondeu X, ver traces lado-a-lado

Comparando versões (a alma da observabilidade)

Quando você muda o agente (prompt, política, prompt) você precisa de uma agent_version nova. No nosso projeto, bump manual em agent/version.py. Aí o Postgres deixa comparar:

# via Makefile
make compare-versions     # lista versões e quantas execuções cada uma tem
make compare v1 v2        # distribuição de decisões lado a lado (com % )

O Phoenix complementa: abre o trace do mesmo ticket nas duas versões e vê, visualmente, onde o comportamento mudou.

Postgres — o diário do agente

-- Schema simples da tabela de execuções
CREATE TABLE execucoes (
    id            SERIAL PRIMARY KEY,
    ticket_id     TEXT NOT NULL,
    agent_version TEXT NOT NULL,
    user_id       TEXT,
    asset_id      TEXT,
    decision      TEXT,           -- 'orient' | 'act' | 'escalate'
    quality_verdict TEXT,         -- 'ok' | 'partial' | 'incomplete' | 'unavailable'
    data_gaps     JSONB,          -- o que faltou
    trace         JSONB,          -- chamadas à API + justificativas
    response      TEXT,
    created_at    TIMESTAMPTZ DEFAULT NOW()
);

Com isso, você pode fazer queries como:

-- Quantas vezes o agente escalou, por versão?
SELECT agent_version, decision, COUNT(*)
FROM execucoes
GROUP BY agent_version, decision;

-- Quais gaps mais comuns?
SELECT jsonb_object_keys(data_gaps) AS gap_category, COUNT(*)
FROM execucoes
GROUP BY gap_category
ORDER BY count DESC;

-- Ticket que levou mais tentativas (retry)
SELECT ticket_id, jsonb_array_length(trace) AS steps
FROM execucoes
ORDER BY steps DESC
LIMIT 5;

Phoenix — o raio-X de cada chamada

O Phoenix (Arize) grava cada chamada ao LLM (input completo, output, tokens usados, latência). Se o LLM respondeu algo errado no TKT-INV-11, você pode abrir o trace e ver exatamente o que entrou e saiu do modelo.

O que o Phoenix mostra que o Postgres não mostra:
  • O prompt completo que foi enviado ao LLM
  • A resposta bruta do LLM (antes do parse)
  • Número de tokens usados e custo estimado
  • Latência de cada chamada
  • Se houve retry por timeout/rate-limit

Phoenix — a visão de cima

O Phoenix (Arize) é um dashboard visual que mostra:

  • Distribuição de decisões (orient/act/escalate) ao longo do tempo
  • Comparação entre versões do agente
  • Traces side-by-side (v1 vs v2 do mesmo ticket)
  • Qualidade das respostas vs dados disponíveis

Como se conectam

Agente executa ticket
    ↓
Postgres: salva resumo (decision, gaps, trace JSON)
    ↓
Phoenix: salva trace detalhado (cada chamada ao LLM)
    → Dashboard em http://localhost:6006

Teste seu entendimento

Pergunta 1
O agente escalou o TKT-INV-11 porque o modelo antigo não tem dados suficientes. Você quer investigar por que o LLM optou por reprocessar em vez de escalar. Qual ferramenta você abriria primeiro?
Resposta

Phoenix. Ele mostra o prompt completo (com os gaps registrados), a resposta bruta do LLM, e se houve algum problema de parsing. O Postgres só guarda o resumo; o Phoenix mostra a visão agregada.

Pergunta 2
Você criou uma v2 do agente e quer comparar com a v1. Quais ferramentas usa?
Resposta

Postgres para comparar métricas agregadas (taxa de acerto por versão). Phoenix para comparar traces lado-a-lado do mesmo ticket (é o raio-X de cada chamada LLM individualmente).
