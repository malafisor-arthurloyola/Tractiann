L2 — O Envelope de Resposta

Toda vez que o agente pergunta algo à API, ele não recebe só "os dados". Ele recebe um pacote (envelope) com três campos. Entender como esse pacote funciona é a diferença entre o agente confiar em dados errados e saber quando parar.

O formato do envelope

{
  "mode": "complete" | "partial" | "inconclusive" | "conflict" | "unavailable",
  "notes": "mensagem explicativa ou null",
  "data": { ... }
}

Os três campos:

  • mode — diz qualidade da resposta (não só o conteúdo).
  • notes — explicação humana do que aconteceu.
  • data — o dado em si (pode estar incompleto, vazio, ou com flag "conflict": true).

Os 5 modos — o que cada um significa na prática

Modo O que chega no data O que o agente deve fazer Probabilidade*
complete Dados inteiros, sem campo faltando Confia e segue ~60%
partial Dados com campos removidos (ex: evidence sumiu da análise) Usa o que tem, anota o que falta. Pode prosseguir. ~15%
inconclusive Só o asset_id + flag "inconclusive": true Não tem dado. Tenta outra tool ou escala. ~10%
conflict Dados originais + flag "conflict": true Duas fontes discordam. Pesa evidência e decide com cautela. ~8%
unavailable {} (dicionário vazio) Dado indisponível. Escala ou busca dado alternativo. ~7%

*Distribuição padrão definida em api/app/prob.py. Com ?seed=complete na URL, força sempre complete (útil para explorar no Swagger durante o desenvolvimento).

Como o modo é decidido pela API

  1. Override de cenário? Ativos como G501 ou S420 têm comportamento fixo definido em seed.json — sempre vêm com modo específico.
  2. Seed especial? ?seed=complete força complete; ?seed=degraded força partial.
  3. Seed comum ou sem seed? O API calcula um hash determinístico (SHA-256(seed|resource|category)) e compara com a distribuição de probabilidades.
Por que isso é assim? Porque no mundo real, dados de sensores industriais nem sempre chegam completos. Às vezes o sensor tá off, o dado tá conflitante, ou tá atualizando. A API simula isso de propósito para treinar o agente a lidar com incerteza — que é o grande diferencial de um bom agente.

O que cada categoria "perde" no modo partial

# Quais campos são removidos em cada categoria quando mode = partial

Teste seu entendimento

Pergunta 1
O agente consulta o baseline do ativo G501 e recebe: {"mode": "unavailable", "data": {}, "notes": "Indisponibilidade temporária..."}. Ele deve:
Resposta

Reconhecer que o dado está indisponível. Não confiar em dado vazio. Tentar outro dado (ex: RMS ou análise) ou escalar se não tiver outra fonte. Nunca inventar um baseline "porque sim".

Pergunta 2
Qual a diferença prática entre inconclusive e unavailable?
Resposta

Inconclusive: o recurso existe, a API tentou processar, mas os dados não sustentam uma conclusão. Só vem o ID. Unavailable: a fonte retornou nada (dicionário vazio). Na prática, o agente escala nos dois casos, mas o notes diz o porquê.

Pergunta 3
Se seed=complete garante respostas completas, por que não usamos sempre?
Resposta

Porque na avaliação (e no mundo real), o agente precisa provar que sabe lidar com dados incompletos. O modo complete é só para explorar a API no Swagger durante o desenvolvimento.
